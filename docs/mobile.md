# bookanything mobile app: architecture

The iPhone, iPad and Android app in `mobile/`. Conventions for people building features on it are in
[`mobile/README.md`](../mobile/README.md); the API contract is still [`architecture.md`](architecture.md) §6 and
`backend/openapi.yaml`.

## 1. Decisions

| Decision   | Choice                                                                                                       | Why                                                                                                                                                                                                                                    |
| ---------- | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Framework  | **Expo SDK 57** (React Native 0.86, React 19.2), new architecture, Hermes                                    | The latest SDK; managed native projects (Continuous Native Generation: `ios/` and `android/` are generated by `expo prebuild`, never committed), EAS for builds and store submission, the same TypeScript/React skills as the website. |
| Navigation | **expo-router** (file-based, typed routes)                                                                   | Routes are files, like the website's App Router, and **the app's URLs are the website's** (`/my/bookings`, `/dashboard/[slug]/bookings`, `/[slug]/book`), so universal links and notification links open the same page in either.      |
| Language   | TypeScript strict + `noUncheckedIndexedAccess`                                                               | The website's settings; the shared code compiles under both.                                                                                                                                                                           |
| Data       | TanStack Query 5 with the **website's own hooks**, persisted to encrypted MMKV                               | One API layer for both apps; instant cold starts from the persisted cache.                                                                                                                                                             |
| Auth       | `@clerk/expo` (hosted sign-in, token in the Keychain) in production; the backend's dev tokens in development | The backend verifies the same Clerk session JWT as for the website (§3.1); dev mode mirrors the website's (§3.2).                                                                                                                      |
| Lists      | FlashList 2                                                                                                  | Recycling lists for long bookings/customers/calendar lists.                                                                                                                                                                            |
| Images     | expo-image                                                                                                   | Disk + memory cache, placeholders, transitions.                                                                                                                                                                                        |
| Icons      | lucide (`lucide-react-native`)                                                                               | The website's icon set, so a screen uses the same symbols on both.                                                                                                                                                                     |
| Tests      | Jest (jest-expo) + React Native Testing Library + expo-router's in-memory router; Maestro for E2E            | Component and whole-app flows in CI without a simulator; real-device flows with Maestro.                                                                                                                                               |

### Why a native app rather than the website in a WebView

The website is a good responsive site, but wrapping it would ship its weaknesses as an app:

- **Feel and speed.** Native navigation stacks, gestures, large titles, haptics, the keyboard, pull to refresh, lists
  that recycle cells: a WebView imitates them and App Review judges "repackaged website" apps harshly (Guideline 4.2).
  The app also opens instantly from its persisted cache, offline included, instead of loading a page.
- **The iPad.** A sidebar and real split views (list beside detail) that follow the window as it's resized in Split
  View and Stage Manager; the website's breakpoints were designed for browsers.
- **Platform features the business side needs**: push notifications, the Keychain for sessions, voice dictation for
  Bo, the share sheet, calendar and maps, universal links, biometric unlock later. Each is a bridge you build anyway
  in a WebView, without native UI around it.
- **Accessibility**: VoiceOver/TalkBack semantics, Dynamic Type and Reduce Motion from native controls.

We still **share the website's logic** (§2): the API client and contract types, query keys, React Query hooks,
formatting, vocabulary, validation, booking rules, permissions and the navigation model. Only the views differ.

### What stays on the website (opened deliberately)

Some flows are better on the web; the app opens them in an in-app browser sheet (`openWebsite`, `src/lib/links.ts`)
or an authentication session:

- **The site builder** (`/dashboard/[slug]/site`): a desktop-sized page editor with live previews. The app's Site
  section explains it and opens it in the **system browser** (`openWebsiteInBrowser`), not an in-app sheet: the
  website's dashboard around it links to Billing, where a plan is bought, and the app must offer no route to that
  (App Store 3.1.1). It goes through the website's `/sign-in?redirect_url=…` (straight on when the browser is signed
  in), which the app doesn't claim as a universal link, so the link isn't handed back to the app.
- **Stripe**: Checkout for paying a booking and Connect onboarding (Settings › Payments) are Stripe-hosted pages;
  the app opens them with `WebBrowser.openAuthSessionAsync` and a return URL back into the app.
- **The bookanything plan** (Settings › Billing) is read-only in the app: it shows the plan, its status and dates,
  what it includes and AI usage, but offers no way to subscribe, change plan or open Stripe's billing portal, no
  other plans' prices and no pointer to buying on the website. A plan is a digital subscription, which the App Store
  (guidelines 3.1.1, 3.1.3) and Google Play only allow through their own in-app purchase; selling it on the website
  only and keeping the app silent about it is the multiplatform-service route. Revisit if we add store billing.
- **Business onboarding** (creating a business) is in the app: the switcher's "Set up a new business" opens a
  wizard (`/onboarding`: describe, AI draft or template, review, create) with no plan or payment step.
- **The OAuth consent page** (`/oauth/authorize`) belongs to the AI app's flow, in its browser.

## 2. Shared code

**Decision: the app compiles the website's platform-agnostic modules in place (`frontend/src/lib`) through an
alias, rather than moving them into an npm-workspace package (`packages/shared`).**

Why, for now:

- The website keeps working exactly as before: no file moves, no import rewrites across hundreds of files, no
  change to its lockfile, install, Turbopack chunking (tuned in `next.config.ts`) or bundle budget. Work in progress
  on the website doesn't conflict with the move.
- There is one source of truth physically, already covered by the website's tests (90% lines) and its OpenAPI
  contract tests; the app's tests exercise it again.
- CI installs only `mobile/` for the mobile job.

How it works (`mobile/shared-code.js`, used by `metro.config.js` and `jest-resolver.js`; mirrored in
`mobile/tsconfig.json` `paths`):

| Specifier        | Points at                 | Used by                                                                                |
| ---------------- | ------------------------- | -------------------------------------------------------------------------------------- |
| `@shared/<path>` | `frontend/src/lib/<path>` | The app's code: `@shared/api/hooks/use-me`, `@shared/format`, `@shared/status`…        |
| `@/<path>`       | `frontend/src/<path>`     | Only the shared modules' own imports (`@/lib/api/types`). Banned in app code (ESLint). |
| `~/<path>`       | `mobile/src/<path>`       | The app's own code.                                                                    |

A package imported by a shared module (`react`, `@tanstack/react-query`, `zod`, `date-fns`, `@date-fns/tz`)
resolves from `mobile/node_modules` (Metro and Jest re-root the request; tsconfig `paths` does it for `tsc`): one
React and one Query client, and no dependency on `frontend/node_modules`.

What is shared today (52 modules, listed by `node mobile/scripts/shared-boundary.js`): the API client
(`configureApiClient` gives the app its base URL and fetch), contract types, query keys, every React Query hook and
`QUERY_DEFAULTS`, `AuthState`/`AuthContext` and the dev token codec, the business context and permissions,
vocabulary, formatting (dates in the business timezone, money), statuses, booking and availability rules,
validation schemas, brand colour maths (`brandPalette`), the dashboard navigation model (`lib/dashboard/nav.ts`:
sections, settings sections, roles).

**Guards** (a shared module must have no DOM or Next.js dependency):

1. The website's ESLint (`frontend/eslint.config.mjs`): every `src/lib` module is platform-agnostic unless listed in
   `WEB_ONLY_LIB`; others may not import Next/react-dom/Radix/lucide-react…, use browser globals (`window`,
   `localStorage`…), render DOM elements, or import a web-only lib module.
2. The app's boundary test (`mobile/scripts/shared-boundary.test.js`, in `npm test`): walks the real import graph from
   the app into the website and fails on web-only packages, website components, browser globals, DOM elements, a
   package the app doesn't depend on (or at another major version), or one missing from tsconfig `paths`. It has a
   selftest, so it can't silently stop failing.

**When to move to a workspace package.** If a third consumer appears, or the shared set needs its own versioning,
move it to `packages/shared` with npm workspaces. The app only changes the `@shared` target; the website changes its
imports from `@/lib/...` to the package.

## 3. App structure

```
mobile/
  app/                       routes (expo-router); thin files that render src/features/* screens
    _layout.tsx              providers, splash, root stack (signed out: Explore, a business, booking, manage links)
    index.tsx                launch: sign-in, or where the person left off (/v1/me)
    sign-in.tsx
    (customer)/              customer experience: adaptive tabs (phone) / sidebar (iPad)
      (explore)/  explore/index, [slug]/index, [slug]/book
      (bookings)/ my/bookings/index, my/bookings/[id]
      (approvals)/my/approvals/index, my/approvals/[id]
      (account)/  my/index, my/notifications, my/connected-apps
    dashboard/index.tsx      picks a business
    dashboard/[slug]/        business experience: adaptive tabs / sidebar; one stack per section
      (overview) calendar bookings customers services resources team offers reports site approvals settings more
    assistant.tsx notifications.tsx connect-ai.tsx    modals over any screen
    manage/[token].tsx invitations/[token].tsx        links from emails
  src/
    config/ api/ auth/ shell/ ui/ lib/ features/<area>/ test/
  e2e/                       Maestro flows
  scripts/                   design-token lint, shared-code boundary
```

The **shells** (`src/shell`): `AdaptiveTabs` is one tab navigator with two presentations: a bottom tab bar on phones
and narrow windows, a sidebar on large screens (`useLayout().isWide`, window width ≥ 700pt). Only the bar is
swapped, so tab history survives rotation and Split View resizing. The business shell (`BusinessShell`) loads the
membership and business, provides the website's `BusinessContextProvider` and `VocabularyProvider`, and shows the
sections `@shared/dashboard/nav` allows the member's role (`businessNav`); on phones the tab bar is the website's
`TAB_BAR_KEYS` plus More. People with memberships switch between their businesses and their own bookings with the
`BusinessSwitcher` (sidebar header on iPad, header avatar on phones).

## 4. Auth

- **Production / preview**: `ClerkProvider` from `@clerk/expo` with its Keychain token cache
  (`@clerk/expo/token-cache`, expo-secure-store). Sign-in uses Clerk's hosted Account Portal in an authentication
  session (`useHostedAuth`), so the sign-in methods and look match the website's Clerk instance. The API client gets
  `getToken()` (the Clerk session JWT), exactly like the website.
  - **Native sessions on the backend**: Clerk sets a session token's `azp` to the `Origin` of the request that minted
    it; `@clerk/expo` sends none, so the app's tokens have no `azp`. The backend accepts them only with
    `CLERK_ACCEPT_NATIVE_SESSIONS=true` (architecture §3.1); tokens that carry an `azp` are still checked against
    `CLERK_AUTHORIZED_PARTIES`, so the website is unaffected. Set it in production when the store build ships, with
    the Clerk instance's Native API enabled (Clerk dashboard › Native applications: the iOS team and bundle ids and
    the Android package and signing SHA-256; allow the app's scheme as a redirect URL).
  - **Deleting the account** (Account › Delete your account; App Store 5.1.1(v), Google Play's account deletion
    policy) calls Clerk's `user.delete()`, so the Clerk instance must allow it (Clerk dashboard › User &
    authentication: let users delete their accounts; the app falls back to the privacy email while it's off). Clerk's
    `user.deleted` webhook then anonymises the user in the backend (`ClerkEventHandler`: AI apps disconnected,
    notifications and push devices forgotten, customer records unlinked with bookings kept by the businesses,
    memberships removed, a business left without an owner suspended). Clerk may ask for a recent sign-in
    (reverification): the app says to sign out and in again. Dev auth has no account to delete. Google Play also
    needs a web page for deletion requests; the website has none yet.
- **Development**: without `EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY` the app uses dev auth: pick a seeded demo account or
  type any email; the token `dev.<base64url(JSON)>` (shared `encodeDevToken`) is kept in the Keychain. Only a backend
  with `APP_ENV=development AUTH_MODE=dev` accepts it. A store build without Clerk shows a configuration error
  instead of the app.
- Either way the app provides the website's `AuthState` through `@shared/auth/context`, so shared hooks and
  components see one contract. Signed in → `GET /v1/me`: memberships decide whether the business experience is
  offered; the app opens the business last used, else My bookings (or Explore for someone new).
- **Signed out**, Explore, a business's page and its booking flow work as on the website (guests book; Sign in in
  the header), as do manage links. Screens that need an account but are opened from links (`/my/…`, `/dashboard/…`,
  `/invitations/…`) go to `/sign-in?returnTo=<path>` and on to it after sign-in (`RequireSignIn`,
  `src/auth/return-to.ts`: only a relative in-app path is accepted). Signing out goes to plain sign-in.

## 5. Data layer and performance

- One `QueryClient` with the website's defaults (`@shared/api/query-defaults`: 30 s stale, no retry on 4xx), 24 h
  memory, persisted with `PersistQueryClientProvider` to MMKV **encrypted with a random key kept in the Keychain**
  (`src/lib/storage.ts`); a new app version or another user starts empty. Queries opt out with
  `meta: { persist: false }`.
- Focus is the app coming to the foreground (`AppState` → `focusManager`); online state comes from expo-network
  (`onlineManager`). Screens also refetch when they regain focus (`useRefetchOnFocus`) and support pull to refresh
  (`usePullToRefresh`).
- React Compiler is on (`experiments.reactCompiler`), so components memoise automatically; Clerk's SDK is loaded only
  in builds that use Clerk.
- Errors: data errors are screen states (`ErrorState`); render errors hit the route `ErrorBoundary`
  (`RootErrorBoundary`) and `logError`, which reports them to Sentry when the build has a DSN (below).

### Errors and crash reporting (Sentry)

`src/lib/error-reporting.ts` starts Sentry (`@sentry/react-native`) at start-up and registers it with the logger's
`setErrorReporter`, so features keep calling `logError` and nothing else knows about Sentry.

- **Off without a DSN.** With no `EXPO_PUBLIC_SENTRY_DSN` the SDK is never loaded or initialised: no network, no
  reporter, `logError` only logs in development. Development, tests and CI need no Sentry account.
- **What is captured:** native crashes, unhandled JS errors and promise rejections, and whatever `logError` reports
  (render errors from `RootErrorBoundary`, unexpected failures in features) with its context. `isReportable` applies
  to the JS side's events: offline, signed out, 4xx and "unavailable" API errors are states, not bugs, and aren't
  sent, except as the cause of a crash (level fatal), which always is. Breadcrumbs (console, the JS side's requests,
  app lifecycle) come along, scrubbed. Errors only: no `tracesSampleRate`, profiling or replay options at all (even
  at 0 they install that machinery), no trace headers on our requests, no screenshots or view hierarchy.
- **Personal data:** `sendDefaultPii: false`. The user is Clerk's opaque user id (`setReportedUser` from the root
  layout); under dev sign-in, whose id is made from the email address, nobody is named. `beforeSend` and
  `beforeBreadcrumb` scrub every JS event and breadcrumb: emails and phone numbers (percent-encoded ones and
  `tel:`/`sms:` links too) in messages, exception values, breadcrumbs and context; the secret in `/manage/<token>`
  and `/invitations/<token>`, secret-looking query parameters (`?token=`…), bearer tokens and JWTs; the query and
  fragment of every absolute URL and of request breadcrumbs (searches and addresses go there); and all of a
  request but its URL (no body, headers or cookies). Failed HTTP requests aren't captured as errors. Native crash
  reports are built by the iOS and Android SDKs and never pass through JS: they carry the JS breadcrumbs already
  scrubbed, iOS's own request breadcrumbs are off, and otherwise they rely on Sentry's server-side scrubbing (below).
- **Environment:** `development`, `staging` (the `preview` variant) or `production`, from `APP_VARIANT`;
  `EXPO_PUBLIC_SENTRY_ENVIRONMENT` overrides it. **Release and dist** are the SDK's defaults:
  `<bundle id>@<version>+<build number>` and the build number (EAS increments it for production).
- **Source maps and debug symbols:** Metro adds debug ids to the bundle and its maps (`getSentryExpoConfig` in
  `metro.config.js`, which also leaves session replay out of the bundle). The Sentry config plugin
  (`@sentry/react-native/expo`), whose build phases upload the maps and native debug symbols, is added only when
  `SENTRY_AUTH_TOKEN` is set, and takes the org and project from `SENTRY_ORG` and `SENTRY_PROJECT`. Without the
  token only the upload is skipped: the native SDK is linked in every build and stays idle without a DSN.
- **EAS environment variables** (per environment, `preview` and `production`):

  | Variable                         | Visibility | Purpose                                                      |
  | -------------------------------- | ---------- | ------------------------------------------------------------ |
  | `EXPO_PUBLIC_SENTRY_DSN`         | plain text | turns reporting on (public by design: it ships in the app)   |
  | `SENTRY_AUTH_TOKEN`              | secret     | organization auth token for source map and symbol upload     |
  | `SENTRY_ORG`, `SENTRY_PROJECT`   | plain text | the Sentry organization and project slugs the upload goes to |
  | `EXPO_PUBLIC_SENTRY_ENVIRONMENT` | plain text | optional: overrides the environment derived from the variant |

  In Sentry: one React Native project (its DSN), an organization auth token (Settings › Developer Settings ›
  Organization Tokens), and in the project's Security & Privacy settings "Prevent storing of IP addresses" and the
  default data scrubbers on: the only scrubbing native crash reports get, and a second line behind the app's own.

In development the app derives the API host from the Metro server it loaded from, so a physical phone on the same
Wi-Fi reaches the Mac's backend with no configuration (`src/config/env.ts`). Public settings go in EAS environment
variables (or `mobile/.env.local` locally, see `.env.example`); nothing secret ships in an app.

**Universal links**: iOS `associatedDomains` and Android `intentFilters` claim `/my`, `/dashboard`, `/manage`,
`/invitations`, `/explore` and a business's booking flow (`/{slug}/book`) (`APP_LINK_PATHS` and `APP_BOOK_PATTERN` in
`app.config.ts`, mirrored by `APP_LINK_PATHS` and `APP_BOOK_PATH` in `frontend/src/lib/app-links.ts`). The website serves the two documents from its server environment, read per request
(`frontend/README.md` §9), and answers 404 while they are unset:

- `/.well-known/apple-app-site-association` from `APPLE_APP_IDS` (comma-separated `TEAMID.bundle.id`): those paths
  and everything under them, plus `webcredentials` so the native Clerk sign-in and passkeys can use the domain.
  Staging: `V266333BR2.ie.bookanything.app.preview`; production: `V266333BR2.ie.bookanything.app`.
- `/.well-known/assetlinks.json` from `ANDROID_PACKAGE_NAME` (staging `ie.bookanything.app.preview`, production
  `ie.bookanything.app`) and `ANDROID_SHA256_FINGERPRINTS` (comma-separated `AA:BB:…`): list both the upload key's
  (EAS keystore, `eas credentials`) and the app signing key's (Play Console › App integrity), with `handle_all_urls`
  and `get_login_creds`.

Because routes mirror the website's paths, an approval link (`/dashboard/{slug}/approvals/{id}`,
`/my/approvals/{id}`) opens the same screen in the app.

**Release lifecycle**: same repository and CI as the website (the `Mobile` job runs format, lint, design-token lint,
typecheck, app config for all variants, and tests with coverage). EAS Build profiles (`eas.json`): `development`
(dev client, internal), `development-simulator`, `preview` (internal, staging), `production` (store, auto-incremented
build numbers, `appVersionSource: remote`). Node 22 on EAS and CI; the app also runs on newer Node locally.

## 7. Testing

- Unit and component tests next to the code (`*.test.ts(x)`), Jest + RNTL with the API stubbed at `fetch`
  (`src/test/api-mock.ts`) so the real client, hooks and query keys run; fixtures are the website's contract-checked
  ones (`@shared/api/__tests__/fixtures/*`).
- Whole-app flows in Jest (`src/test/app.tsx` renders the real `app/` routes in memory): launch → dev sign-in → My
  bookings, role-based navigation, guards, iPad sidebar, sign-out.
- Maestro flows (`mobile/e2e/flows`) on a simulator or device against the local backend with seeded data.
- Coverage thresholds in `jest.config.js` (never lowered to pass a build).

## 8. Bo, notifications and AI apps

### 8.1 Bo and voice (`src/features/assistant`)

- The website's Bo (architecture §17) on top of the same shared state machine and hooks (`@shared/assistant/*`,
  `use-assistant`): home (nudges, quick actions, recent conversations), the chat, memory, credits and the "AI isn't
  configured" state. A modal on phones (`/assistant?business=<slug>`, optional `&ask=`), a side panel beside the
  sections on wide windows (`AssistantDock`, in the business shell). Proposal cards keep the website's semantics:
  nothing changes until Confirm; the card then shows the result and its links.
- **Streaming**: React Native's `fetch` buffers bodies, so the API client uses `expo/fetch` (`src/api/setup.ts`), whose
  responses stream; `TextDecoderStream` comes from Expo's runtime. The log is a FlashList anchored to the end; only the
  live reply re-renders while it streams (`useDeferredValue` absorbs bursts). Screen readers aren't fed every chunk:
  the live reply is marked busy and the finished one is announced once.
- **Dictation**: tap the microphone to dictate until tapped again, or hold to talk and let go. On-device recognition
  where the device has it (`expo-speech-recognition`, `requiresOnDeviceRecognition`), otherwise Apple's or Google's
  service, and the composer says which while it listens. Language: the business's locale. Words appear in the box as
  they are heard; nothing is sent until Send. The rules are a pure state machine (`dictation/dictation-logic.ts`,
  adapted from multicode-mobile's `dictationLogic`: restarts after pauses, repeated words, permissions, errors) run
  by a controller with a fake recogniser in tests. Haptics on start/stop/error; states announced.
- **Hands-free** (off by default, kept on the device): Bo reads each finished reply aloud (`expo-speech`, the
  business's language); dictating, sending or closing Bo stops it, and it stays quiet while VoiceOver/TalkBack is on.
- Purpose strings (app.config.ts plugins): the microphone is used only while dictating, audio isn't kept, and nothing
  is sent until Send.

### 8.2 Notifications and push (`src/features/notifications`)

- The bell (`HeaderActions`, unread count) opens the inbox modal (`/notifications`); `/my/notifications` lists them
  with the email choices. Opening one marks it read and goes where its link goes: the app's routes are the website's
  paths (`links.ts`; `/dashboard/x/bookings?booking=id` opens the booking's own screen; anything else stays on the
  website; full URLs are refused).
- **Push** (`push/`): `PushNotifications` (mounted in `app/_layout.tsx`) shows pushes as banners while the app is
  open and refreshes the bell, opens a tapped push's link (also from a cold start) and marks it read, keeps the icon
  badge at the unread count, and registers the phone (`POST /v1/me/push-devices`) when signed in with permission
  (on launch, at most daily). Sign-out unregisters it first (`DELETE /v1/me/push-devices`, via
  `src/auth/before-sign-out.ts`). Signed out with the phone still registered (the session expired or was revoked
  elsewhere, or sign-out was offline), the app turns push off on the phone (`unregisterForNotificationsAsync`: Expo
  then answers `DeviceNotRegistered` and the backend drops it), forgets the registration and clears the badge; if that
  fails, the next launch tries again, and the next sign-in gets a fresh token. Permission is never asked at launch:
  the inbox and the notifications page explain what it's for and ask on **Turn on** ("Not now" waits 30 days; refused
  → a way to Settings).
- **Lock screen**: a push says only the business's name and the kind ("New booking", "A booking was cancelled", …),
  never who, what or when; the app shows the rest. The Android channel is `PRIVATE` on the lock screen, and Android's
  notification icon is `assets/images/notification-icon.png` (white on transparent, the app icon's two pills).
- **Backend**: `PUSH_NOTIFICATIONS=expo` sends through the Expo Push API (`EXPO_ACCESS_TOKEN` if the Expo project
  enables enhanced push security); `log` (development default) logs what it would send, so everything works locally
  up to the delivery itself; `off` elsewhere by default.
- **What real delivery needs** (none of it is in the repo):
  1. An EAS project: `eas init`, then `EAS_PROJECT_ID` in the EAS environment (app.config.ts `extra.eas.projectId`).
     Expo push tokens are per project; without it the app registers nothing.
  2. iOS: an APNs key (Apple Developer › Keys, "Apple Push Notifications service") uploaded with `eas credentials`
     (or let EAS create it), for each bundle id (`ie.bookanything.app`, `.preview`, `.dev`). Builds carry the
     `aps-environment` entitlement (development for the dev client, production otherwise).
  3. Android: a Firebase project with the Android apps, `google-services.json` (`android.googleServicesFile`) and an
     FCM V1 service-account key uploaded with `eas credentials`.
  4. The backend: `PUSH_NOTIFICATIONS=expo` (and `EXPO_ACCESS_TOKEN` when enabled).
  Simulators: iOS simulators can receive pushes only through `xcrun simctl push`; real tokens need a device.

### 8.3 Connect an AI app (`src/features/connect-ai`)

`/connect-ai?server=customer|business` shows the server URL (`<web origin>/mcp` or `/mcp/business`) with Copy, and the
steps from the website's help pages. **Claude** documents an install link that opens its "Add custom connector"
dialog with the name and URL filled in, for the person to confirm
(`https://claude.ai/customize/connectors?modal=add-custom-connector&connectorName=…&connectorUrl=…`,
claude.com/docs/connectors/building/directory-vs-custom); being an https link on claude.ai, it opens the Claude app
where the app handles it, else the browser. **ChatGPT** documents no such link (developers.openai.com/apps-sdk/deploy/
connect-chatgpt starts at chatgpt.com/plugins), so the app copies the URL and opens that page. No custom URL schemes
or undocumented parameters are used. A development build's http address is flagged: AI apps need the public site.
